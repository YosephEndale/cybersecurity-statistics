Classical cipher · Elliptic-curve cryptography · Cryptanalysis

Encryption, decryption and statistical attacks.

This assignment compares the Caesar cipher with a small EC-ElGamal-style demonstration using secp256k1. It implements both encryption and decryption, tests letter-frequency analysis, and shows why a deliberately restricted private-key range makes an elliptic-curve scheme vulnerable to brute-force search.

Scope note. secp256k1 is an elliptic curve, not an encryption algorithm by itself. The page defines a simple ElGamal-style construction over that curve for educational purposes. Ethereum commonly uses secp256k1 for digital signatures; this page is not describing Ethereum transaction encryption. Do not use this demonstration to protect real messages or keys.

01 / Elliptic-curve scheme

Encrypt and decrypt a message

The curve parameters are secp256k1, but the private key is restricted to 1–1,000 so that the attack can be demonstrated quickly.

Educational limitation: the implementation uses browser-generated random ephemeral scalars, but the private-key range is intentionally tiny and the JavaScript arithmetic is not designed to be constant-time. This is a learning example, not production cryptography.

The secp256k1 curve is defined by y² ≡ x³ + 7 (mod p), where p = 2²⁵⁶ − 2³² − 977. The standard generator point is G and has a large prime order n. This page uses the standard curve parameters, but limits the private scalar to 1–1,000 only for the key-recovery experiment.

02 / Classical cipher

Caesar cipher: encryption and decryption

A Caesar cipher shifts each letter by a fixed number of alphabet positions. Uppercase and lowercase are preserved; spaces and punctuation remain unchanged.

The default message is ready to encrypt.

Why is Caesar easy to break?

There are only 26 possible shifts (including a shift of zero). An attacker can test every key, or compare letter frequencies with expected frequencies in the known language. The cipher merely permutes letter identities, so it preserves the overall frequency profile, just under shifted labels.

METHOD A

Exhaustive search

Try every shift from 0 to 25. The key space is so small that this is already practical and does not depend on language statistics. A human still has to identify the readable plaintext.

METHOD B

Frequency scoring

This page uses a chi-square score to compare the candidate plaintext's letter counts with typical English frequencies. The lowest score is treated as the best candidate, not as a guarantee.

Limitations. Short ciphertexts have noisy letter counts; names, technical terms, unusual writing styles and a mismatch between the assumed and actual language can lead to the wrong key. N-gram scoring (using common pairs or triples of letters) can improve ranking, but it is not necessary for this basic experiment and it can also fail on very short texts.

05 / Restricted-key attack

Why the toy ECC key can be recovered

The attack checks d = 1, 2, 3, … and calculates dG until the result matches the public point Q.

In the demonstration, the private scalar is selected from only 1,000 candidates. This is approximately log₂(1,000) ≈ 10 bits of key-space uncertainty. Because scalar multiplication is easy to compute in the forward direction, an attacker can enumerate the permitted candidates and compare each candidate public point with Q. After recovering d, the attacker can decrypt the saved ciphertext.

With a properly generated secp256k1 private key, the scalar is selected from a range of roughly 2²⁵⁶ values. Direct exhaustive search over that range is infeasible. Generic discrete-log algorithms reduce the work compared with naive exhaustive search, to roughly 2¹²⁸ group operations for a 256-bit prime-order group, which is still infeasible in practice with current classical computing.

Important distinction: the immediate weakness in this experiment is the restricted private-key range. Separately, the demonstration lacks authentication and uses simple character-to-point encoding; it should not be treated as a complete, production-ready encryption protocol.

06 / Final remarks

Conclusion

In this assignment, I implemented encryption and decryption using a Caesar cipher and a toy EC-ElGamal-style scheme over secp256k1. The Caesar cipher uses a single shared shift, and its small key space makes exhaustive search straightforward. Its letter-frequency pattern is also preserved under a shift, which allows a statistical attack to rank likely plaintexts.

The elliptic-curve example uses a private scalar and corresponding public point. Each character is encoded as a point, encrypted with a fresh ephemeral scalar, and recovered using the private key. The restricted-key experiment shows that the public key does not protect a weak secret: testing all 1,000 candidates is enough to recover the private scalar and decrypt the message.

The main conclusion is that statistical analysis can reveal weaknesses in simple substitution ciphers, while key-space analysis is the decisive attack against this deliberately restricted ECC example. A full-size key space is essential, but it does not by itself make an arbitrary construction secure. Real systems also need reviewed protocols, reliable randomness, authentication, and careful implementation.
