Homework 2 / Cryptographic primitives

From a wallet seed to an Ethereum address.

This assignment examines the standards involved in generating an Ethereum wallet address, the role of each cryptographic operation, and the statistical properties we can meaningfully study.

The discussion concerns conventional Ethereum externally owned accounts (EOAs) derived from a BIP-39 mnemonic. Not every Ethereum wallet uses exactly the same recovery or derivation method.

01 / Process

The wallet derivation pipeline

The steps below have different roles. They should not be treated as one algorithm.

  1. 01
    Random entropy → Mnemonic

    BIP-39 represents randomly generated secret entropy as a sequence of recovery words with checksum information.

  2. 02
    Mnemonic → Seed

    BIP-39 applies PBKDF2-HMAC-SHA512 (2,048 iterations) to produce a 512-bit seed. An optional passphrase changes the result.

  3. 03
    Seed → Derived private key

    BIP-32 derives a master key and child keys; BIP-44 defines a conventional path for choosing an account and address.

  4. 04
    Private key → Public key

    secp256k1 elliptic-curve multiplication computes the public point Q = kG, which is also used with ECDSA digital signatures.

  5. 05
    Public key → Ethereum address

    Keccak-256 hashes the 64-byte public-key coordinates (x || y, without the 0x04 prefix). The last 20 bytes form the address.

  6. 06
    Address → Checksummed address

    EIP-55 uses a Keccak-derived capitalization pattern for the hexadecimal address to help detect typing mistakes.

Common Ethereum derivation path

m/44'/60'/0'/0/0

m = master key; 44' = BIP-44 purpose; 60' = Ethereum coin type; 0' = account; 0 = external chain; 0 = address index. The apostrophe indicates hardened derivation. Wallets may choose other paths.

04 / Concepts

Different operations, different purposes

OperationMeaning in the wallet
Key generationCreating new secret material from secure randomness, such as the initial entropy for a recovery phrase.
Key derivationDeterministically calculating wallet keys from existing secret material using BIP-39 and BIP-32.
Public-key cryptographyCalculating Q = kG and verifying signatures using the corresponding public key.
HashingConverting input data into a fixed-size digest, as Keccak-256 does during address derivation.
ChecksumDetecting accidental errors; the EIP-55 case pattern is not a digital signature.
EncodingRepresenting bytes as readable characters, such as the hexadecimal text of an address.

The techniques complement one another. A hash function cannot replace the signature scheme, while elliptic-curve multiplication does not provide mnemonic backup, deterministic account organization, or address error detection.

05 / Statistics

Statistical observations

Statistical measurements describe observable behavior. They do not, by themselves, prove cryptographic security.

Bit distribution

For a uniformly distributed hash output, each bit has a probability close to ½ of being 1. For a single output, the observed number of ones may differ from half without indicating a weakness.

Avalanche effect

Changing one input bit in a well-designed cryptographic hash is expected to change roughly half the output bits on average. The Hamming distance measures the number of different bit positions.

Addresses and checksums

An Ethereum address is 160 bits (40 hexadecimal digits). Keccak-derived address values are expected to look well distributed, while EIP-55 capitalization is deliberately structured for error detection.

SMALL REPRODUCIBLE EXPERIMENT / SHA-512

Changing one input bit

The ASCII strings Ethereum and ethereum differ by one bit in their first character (E = 0x45, e = 0x65). Both strings were hashed using SHA-512, and their 512 output bits were compared.

260 / 512different output bits

The observed Hamming distance was 260 bits. For two independent, uniformly random 512-bit strings, the expected distance would be 256 bits. One comparison is illustrative rather than a statistical security test.

Why SHA-512? SHA-512 is a component of HMAC-SHA512 used in BIP-39 and BIP-32. This experiment tests the ordinary SHA-512 hash function; it does not reproduce HMAC, Keccak-256 or the address-derivation process.

SHA-512, Keccak-256 and SHA3-256

SHA-512 belongs to the SHA-2 family and produces 512-bit digests. Keccak-256 and SHA3-256 share the Keccak sponge design and produce 256-bit digests, but differ in padding/domain separation. Therefore, Keccak-256 ≠ SHA3-256. Ethereum address derivation specifically requires Keccak-256; substituting SHA3-256 would produce the wrong address.

07 / Final remarks

Conclusion

This assignment shows that an Ethereum wallet address is the result of several distinct operations rather than a single cryptographic algorithm. BIP-39, BIP-32 and BIP-44 make keys recoverable and organized; secp256k1 establishes the public/private key relationship; Keccak-256 derives the address; and EIP-55 adds an error-detection convention.

The practical test vector confirms how these steps fit together. The SHA-512 comparison also illustrates how a one-bit input change can alter many output bits. However, one observed Hamming distance or an apparently balanced bit distribution is not evidence that a complete wallet implementation is secure. Sound cryptographic design, correct implementations and secure handling of recovery phrases remain essential.
